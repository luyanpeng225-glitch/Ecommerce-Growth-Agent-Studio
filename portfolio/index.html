为什么做 Why

业务背景BUSINESS CONTEXT

从分散协作到可审计工作流

电商运营团队需要把商品 Brief、用户洞察、卖点、平台策略、创意结构、视觉规划、合规审核、人工审批和评估口径串成一条可交接链路。当前案例商品为运动相机，项目类型为 ToB Agent Workflow Demo。

业务痛点BUSINESS PROBLEM

信息、风险和复盘链路容易断开

  • 运营人员需要从商品资料、平台要求和素材清单中反复整理字段，Brief 必填字段缺失时必须阻断下游 Planner。
  • 性能声明、授权素材与结果承诺常在内容完成后才被发现，能力声明缺证据时不能进入最终公开表达。
  • 缺少统一输入输出、risk_id、claim_id、审批记录和测评口径时，很难解释 Agent 为什么得出结论。
  • 结构化输出不能被误读为已批准营销内容。

ARCHITECTURE DECISIONS

架构设计决策

Planner 只负责编排

设计选择：Planner 负责路由、风险预算、回退和交接结构，不直接生成创意。

理由：把编排质量和创意质量分开，便于定位失败与评估。

职责单一的 Agent/Skill

设计选择：用户洞察、卖点、平台、创意、视觉、合规、审批、评估和报告分工明确。

理由：每个节点有清晰 I/O、状态和证据来源，减少黑盒交接。

Two-stage Compliance

设计选择：同一个 Brand Compliance Agent 执行 pre-check 与 post-generation check。

理由：前置拦截缺证据和授权问题，后置检查新增声明、视觉风险与追踪缺口。

Human Approval

设计选择：Human Approval 位于结构化生成结果和发布之间。

理由：事实证明、素材授权、品牌责任和发布准备度必须保留人工判断。

单一 Image Prompt Skill

设计选择：只保留一个视觉结构 Skill，不生成最终图片 Prompt 或图片。

理由：当前范围只需要管理视觉结构、素材依赖和受控生成前置条件。

不采用单一 LLM 或 Multi-Agent Debate

设计选择：不用一个模型一次性完成全部任务，也不用辩论作为核心机制。

理由：本项目优先证明职责边界、审计、审批、WorkTrace 和评估，而不是生成一段难追责的综合回答。

证据口径说明
  1. 实测 · Measured当前项目中可直接检查的文件、字段或构建结果，不代表真实业务增长效果。
  2. 确定性验证 · Deterministic由验证脚本、JSON 解析或 Schema 规则得到的确定性结果。
  3. 产物派生 · Artifact derived根据已有历史产物汇总得到，不是真实运行时 telemetry。
  4. Mock 派生 · Mock derived来自 Demo 或 Mock 数据，只用于展示流程，不能证明客户效果。
  5. 估算 · Estimated来自 Demo 假设或估算，不能写成真实效率提升。
  6. 需人工审核 · Human review仍需要正式证明、素材授权、人工判断或签核后才能成立。
  7. 暂不可用 · Not available当前缺少可靠数据、真实日志或授权证明，系统没有补造。
